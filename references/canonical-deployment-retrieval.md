# Canonical Deployment, CRM Load, and Retrieval Runbook

This runbook provides the vendor-neutral operational boundary after the
canonical export has been created. It is deliberately independent of a specific
CRM, cloud vendor, vector database, or ChatGPT workspace.

The optional typed analytics and governed target-change layer is configured
above this immutable snapshot and does not alter its admission contract. Read
[Business Data Platform](business-data-platform.md) for client YAML, semantic
datasets, analytical exports, proposal journals, and target adapters. A
reconciled target change requires a newly approved canonical export and a new
snapshot before it appears here.

## Canonical export contract

`scripts/canonical_export.py` produces the export from retained run artifacts —
the intake manifest, consensus, arithmetic, and the final-review queue. A
document reaches it only with retained intake provenance (`source_file`,
`source_page_range`, `source_sha256`), a `review_status` in the three
review-clear values, arithmetic that is `proved` or `not_applicable`, and no
open final-review item. Everything withheld is retained in a companion
exception artifact naming the control that withheld it; an agreed extraction
field with no canonical column is withheld rather than mapped, because choosing
its column is a client mapping decision. The command approves nothing: it only
refuses to carry what the review has not cleared, so an export with no rows is
the normal state of a batch whose review is still open.

The controlled input is a JSON object with `batch_id`, optional
`registry_version`, and `tables`. Every table value is a list of rows. Each
batch-managed canonical business row carries the export `batch_id`, its primary
or composite idempotency key, and a supported `review_status`; duplicate keys in
one export are rejected. Evidence-bearing rows retain source-document or explicit
decision provenance. Static reference and role rows retain their own idempotency
keys and may omit `review_status`; when any canonical row supplies that field,
including a vocabulary or association/history row, it must be review-clear.
`load_manifest` entries are generated by the target adapter after
reconciliation. The canonical DDL is
`assets/canonical_schema.sql`; it uses PostgreSQL types, foreign keys,
append-only amendments whose attempted mutation raises an error,
natural/primary-key idempotency, and a `load_manifest` keyed by
`(batch_id, load_step, entity)`.

`source_sha256` on `document` is the immutable fingerprint used by retrieval
citations. Preserve it from the source/page manifest; never replace evidence
with a normalized record.

## Deployment and load planning

```bash
# Plan the PostgreSQL deployment without a database credential in the artifact.
python scripts/canonical_deploy.py --out canonical_deployment_plan.json

# Only an authorized operator with psql and CANONICAL_DATABASE_URL may execute.
python scripts/canonical_deploy.py --out canonical_deployment_plan.json --execute

# Build the export itself from the run's retained artifacts.
python scripts/canonical_export.py --manifest ingestion_manifest.json \
  --consensus consensus.json --arithmetic arithmetic.json \
  --final-review final_queue.json --classifications classification_consensus.json \
  --batch-id "$BATCH_ID" \
  --out canonical_export.json --exceptions canonical_export_exceptions.json

# Verify ordered, idempotent CRM load steps before selecting a CRM adapter.
python scripts/canonical_load.py canonical_export.json --out canonical_load_plan.json
# Create a no-send CSV/API target package; a downstream receiver must reconcile
# every step checksum and idempotency key before an actual load.
python scripts/csv_api_staging.py canonical_export.json canonical_load_plan.json --out crm_staging_run/
# Optionally create common CRM object files and the target-owner write plan.
python scripts/crm_import_package.py canonical_export.json canonical_load_plan.json --out crm_import_run/
```

The deployment command writes its non-secret plan before execution. The load
planner validates every table name, primary key where applicable, batch lineage,
and the review-clear statuses `auto_accepted`, `sampled_verified`, and
`exception_resolved`. Batch-managed rows must supply one; any supplied status
on every other row is held to the same allow-list. `open_exception` is always
rejected and there is no planning or staging override. Before checksums are created, each document must
carry its source file, page range, and SHA-256, and every transactional child
must resolve through the table-driven direct-document/parent-key policy in the
artifact contract. Approved source-independent vocabulary/master tables are the
only documented exception. A supplied broken or legacy-override plan is
rejected in full. Both the plan and the staging manifest record their own total
record count and state explicitly when it is zero, so a package of headings-only
CSVs cannot be reconciled as a completed load. A target CRM adapter must consume the verified plan, use the
recorded idempotency key, halt on foreign-key failure, reconcile row
counts/checksums, and retain the load manifest. It must not silently drop
rejected rows.

`csv_api_staging.py` is the selected target-neutral staging adapter. It creates
ordered CSVs and a versioned API operation envelope but never opens a network
connection or sends credentials. It recomputes the strict plan for the exact
export and rejects any supplied `include_open_review` field rather than
recreating a plan from caller-controlled behavior. It builds in a temporary
sibling directory, writes declared canonical headings even for empty tables,
records bytes, rows, columns, idempotency keys, canonical-row checksums, and file
checksums. Every CSV data row also carries authoritative compact canonical JSON
and its SHA-256, so verification reconstructs the exact source row rather than
trusting presentation cells or a self-reported manifest. It reopens every
artifact, requires the exact ordered file and receiver-operation topology, and
only then atomically publishes the new package directory. A partial package is
never presented as completed.

The v3 envelope marks `api_upload_permitted=false`, distinguishes formula-safe
display cells from the authoritative row JSON, percent-encodes the batch identity
inside endpoint templates, and defines per-table stage/reconciliation/rejection
endpoints, halt-on-rejection behavior, a batch rollback endpoint, and the exact
receiver fields required to account for every attempted, loaded, and rejected
row. Its companion manifest binds the source export, semantic load plan,
envelope, and all CSV files with a package-content checksum. An actual receiver
must be separately selected and accepted before using that contract; neither
this package nor the read-only API or MCP performs a target-CRM write.

`crm_import_package.py` adds an optional, still no-send last-mile package for
teams that need familiar import objects rather than all 28 canonical tables. It
creates twelve ordered CSVs for accounts, contacts/addresses/roles, products,
locations, shipments, transactions/lines/charges, payments, and applications.
Every row retains its exact canonical table, idempotency key, authoritative row
JSON, and row hash. Its manifest explicitly accounts for every canonical table,
including tables outside the common profile, and binds a tenant-completion
mapping worksheet, official vendor-source list, and approval-gated write plan.
Vendor field suggestions are proposals only. See
[`crm-write-readiness.md`](crm-write-readiness.md) for target discovery,
sandbox/idempotency testing, reconciliation, rollback, and separate production
authorization requirements.

## Retrieval database and local MCP

```bash
# Builds a new SQLite FTS5/CRM snapshot from approved canonical facts only.
python scripts/retrieval_store.py build canonical_export.json --out business_retrieval.sqlite
python scripts/retrieval_store.py query business_retrieval.sqlite "invoice INV-1001"
python scripts/retrieval_store.py get business_retrieval.sqlite DOCUMENT_ID

# Read-only JSON-RPC MCP over stdio for local clients and acceptance tests.
python scripts/retrieval_mcp.py business_retrieval.sqlite
```

The retrieval store creates one factual chunk per approved canonical document,
including linked invoice/line facts and approved ACK, job, attribution, and
selling-location context. It also embeds the complete validated canonical export
as an immutable CRM snapshot with unique idempotency-key lookup, per-row hashes,
per-table row-count/checksum manifests, table-order indexes, metadata hashes,
and a separate cross-table FTS5 record index joined back to the authoritative
row store. The database is built in a temporary sibling, passes SQLite integrity
checking, and is published without replacing an existing destination. It
rechecks the applicable table count/checksum manifest before table queries,
exact record lookup, or indexed CRM search, and verifies each returned record
hash before returning it. It
includes document ID, source file, page range, source hash, batch ID, registry
version, and review status as the citation. It always excludes raw LLM responses,
unapproved semantic suggestions, and open-review records; the retrieval builder
first runs the strict canonical load validator and has no override for this
factual boundary.

By default the local MCP exposes the following read-only tools, and the HTTPS API exposes
the same business functions. The private internal sidecar `retrieval_sidecar.py`
wraps the same semantic layer for localhost or same-task HTTP clients:

- `search_business_documents(query, limit)`
- `get_business_document(document_id)`
- `get_crm_capabilities()`
- `get_crm_export_summary()`
- `get_crm_schema(table?)`
- `search_crm_records(query, tables?, limit?)`
- `get_crm_record(table, key)`
- `query_crm_records(table, filters?, select?, sort?, limit?, offset?)`
- `export_crm_table(table, limit?, offset?, filters?)`
- `get_account_card(party_key|name)`
- `analyze_sales(group_by?, filters?)`
- `run_crm_report(report, parameters?)`

Every tool in that baseline list is read-only. The stdio server supports MCP 2026-07-28
`server/discover`/per-request metadata and legacy 2025 `initialize` clients. It
advertises titled input/output schemas plus read-only, non-destructive,
idempotent, closed-world tool annotations and returns structured content beside
the portable JSON text representation. It returns standard JSON-RPC parse,
request, method, parameter, and unsupported-version errors. The database uses SQLite FTS5 so it has no hosted vendor or
embedding dependency. A later vector index/reranker can be built from these
same approved chunks and citations, but must retain the same exclusion and
citation rules. The OAuth-protected remote MCP exposes these twelve tools and
adds owner-bound `create_crm_export` and `get_crm_export_job` tools.

### Optional intake is not canonical write access

`--ingestion-dir` adds eleven source/proposal operations to the MCP servers and
eleven OAuth JSON API routes on the remote server. It stores original PNG/JPEG
pages, source-linked model readings, rejections, reviewer grants, and idempotent
receipts in a separate private journal. Local discovery then has 23 tools;
remote discovery has up to 25 filtered by CRM and
`ingestion:read`/`ingestion:submit` scopes.
The TLS/bearer GET API and the default local shell launcher stay unchanged.

Use [Visual Intake](visual-ingestion.md) for exact setup, request schemas,
limits, source-only export/verification, and acceptance. A proposal's
`pending_review` state is never an approved canonical review status. The local
source exporter prepares an auditable image PDF for normal profiling/intake;
it does not convert model readings to consensus input, write an approved row,
or update a served snapshot. The source package and common CRM import package
are different artifacts with different eligibility rules. Governed business
record delivery and expanded analytics are implemented as the separate
client-configured [Business Data Platform](business-data-platform.md); its
delivery history and remaining client-specific acceptance work are in the
[roadmap](business-data-platform-roadmap.md).

### Query and reporting model

Use indexed `search_crm_records` first when the client knows a name, number,
address fragment, ACK, job, or other text but not its canonical key. Use
`get_crm_record` when the table and its single or composite idempotency key are
known. `query_crm_records` is the governed slice-and-dice surface for one table:
it supports up to ten conditions (`eq`, `ne`, `contains`, `starts_with`, `in`,
`gte`, `lte`, and `is_null`), an explicit field projection, up to three sort
fields, and stable bounded pagination. It never evaluates caller SQL, formulas,
or code.

`get_account_card` returns one approved party with its role history, source-name
variants, addresses, contacts, invoice/payment activity summary, the underlying
approved activity rows, and source documents. Monetary summaries are separated
by currency; a single scalar total is suppressed when unlike currencies would
otherwise be combined. It is the preferred way to pull a client-ready address
or contact card without making the caller reconstruct relationships.

`analyze_sales` is the reusable semantic aggregation surface. It groups approved
invoice counts, total value, amount due, average invoice value, and source
document IDs by up to three of `company`/`customer`, `vendor`, `region`,
`selling_location`, `month`, `quarter`, `year`, `currency`, `ack_number`, or
`job_number`. Filters cover dates, the same business dimensions, and minimum or
maximum invoice value. Currency is always an effective grouping dimension even
when the caller omits it, so unlike currencies are never added together. This
supports sales by company and region, regional or office trends by quarter,
customer/job drill-down, and similar combinations without exposing arbitrary
SQL.

The built-in deterministic report catalog supplies:

- `account_directory`
- `invoice_register`
- `receivables_aging` (requires an explicit `as_of` date, buckets the current
  approved balance snapshot, excludes later invoices, and does not reconstruct
  historical balances)
- `sales_by_customer`
- `sales_by_selling_location`
- `attribution_coverage`
- `shipment_performance`

Customer/location sales reports and invoice-attribution coverage are partitioned
by currency; attribution coverage counts only non-failure attribution rows whose
target resolves to an invoice. Every table page, exact record, account card, analysis, and report binds the
canonical source-export hash and includes its own stable checksum. Aggregated
rows retain contributing source document IDs. This is the recommended client
architecture: one approved canonical snapshot, one shared semantic service,
local and remote MCP transports plus the REST API, and no duplicated query
logic.

### Authenticated HTTPS retrieval

`scripts/retrieval_https.py` provides the complementary remote transport. It is
disabled by default, binds to `127.0.0.1` by default, requires a TLS certificate
and private key, and requires a dedicated bearer token named by
`RETRIEVAL_HTTPS_CREDENTIAL_ENV`. It exposes `GET /health`, capability discovery,
document search/get, CRM summary/schema/search/exact-record/query/export,
account-card, sales-analysis, report-catalog, and report-run routes over the
same approved-facts SQLite database used by MCP. It implements no write route,
rejects `POST`, `PUT`, `PATCH`, and `DELETE`, rejects unknown/repeated parameters
at the closed-world boundary, and sets `Cache-Control: no-store` plus
`X-Content-Type-Options: nosniff`.

For a co-located application or ECS task, `scripts/retrieval_sidecar.py` serves
the same approved-fact retrieval/report boundary through a small private
`FastAPI` listener. It is intended for `127.0.0.1` or task-local networking, not
public exposure, and reads its immutable snapshot from `RETRIEVAL_DB_URL`,
`RETRIEVAL_ARTIFACT_ROOT`, or `--database`.

```bash
# Only after client transport, TLS, token distribution, host, and retention approval.
python scripts/retrieval_https.py business_retrieval.sqlite --enable \
  --certificate /restricted/tls.crt --private-key /restricted/tls.key
```

The existing `retrieval_mcp.py` stdio service remains read-only by default;
its optional image/proposal journal is separate from approved-fact retrieval.
An internet-facing host, DNS, reverse proxy, certificate issuance, firewall,
rate limiting, tenant boundary, monitoring, and incident response are deployment
acceptance work; they are not silently assumed by the local endpoint.

### OAuth-protected remote MCP and downloadable reports

`scripts/retrieval_remote_mcp.py` is the remote MCP transport for Claude and
ChatGPT mobile/web/desktop connectors. It is disabled by default, serves
stateless Streamable HTTP at `/mcp`, requires TLS plus RFC 7662 token
introspection, and binds the process to one exact HTTPS resource, tenant, and
immutable approved-fact snapshot. Each request enforces token activity, expiry,
audience, subject, tenant, allowed role, and `crm:read` or `crm:export` scope
before a business handler runs. It also applies request-size, client-address
rate, and optional Origin bounds and writes content-free audit events.

The remote-only `create_crm_export` tool accepts exactly one approved table or
standard report plus bounded filters/parameters and creates CSV or XLSX. The job
manifest records the snapshot/source hashes, canonical row checksum, file
checksum, requester hash, exact arguments, size, row/column counts, and expiry.
Every spreadsheet cell is written as a display string with formula-leading
values neutralized. `get_crm_export_job` is owner-bound. The returned random
download token is stored only as a hash, the short-lived download is checksum-
verified, and expired, mismatched, unknown, or modified artifacts fail closed.
Every page must retain the source-export hash captured when the job began;
cross-snapshot pagination is refused. The private export root rejects group or
other permissions, partial failed jobs are removed, and status/download fully
validate the closed manifest before reading an artifact. No export changes the
snapshot or performs a target-CRM write.

The remote endpoint supports both the 2025 initialize era and MCP 2026-07-28.
For the modern era, protocol metadata and `Mcp-Method`/`Mcp-Name` headers must
agree with the JSON-RPC body, and successful results carry the required
completion marker. Use the exact public `/mcp` URL as the OAuth resource and
audience; the path-specific RFC 9728 metadata location is published alongside
the root fallback.

### Portable MCP configuration hook

The tracked `mcp/retrieval.mcp.json.example` is a generic stdio MCP configuration. Copy it into the configuration location used by an MCP-compatible client and replace `<REPOSITORY_ROOT>` and `<RETRIEVAL_DATABASE_PATH>` with absolute local paths. It calls the tracked `scripts/run_retrieval_mcp.sh` launcher, which selects the project virtual environment when present and never writes to the database. The exact client configuration location and any remote transport, authentication/tenant isolation, deployment environment, or client-workspace registration remain separately authorized integration work; they are not implied by this local hook.
